# Fence race fix — verification (labelled diagnostics, not the official qualification)

Everything below ran in owned, serial containers under the R8 envelope, outside the gate:
builder `14ea7861…` (4 CPU, 6 GiB, swap = memory, pids 256, `CARGO_BUILD_JOBS=2`) and test
`13d68aa0…` (2 CPU, 2 GiB, swap = memory, pids 128); network none, read-only root, init, log
driver none, core 0, tmp 64 MiB; `/work` read-only except the owned subpath
`/work/orchard-m27-pages-mrt-fence`; the R8 `gpu_env` verbatim (Runtime26/LLVM21 Lavapipe,
`mrt-fetch-validation-layer-v2`, Core + SYNC); host-space sample read through
`host-space-io/Read-HostSpaceSample.ps1` every 0.2 s outside and inside each container.
Every test process had both streams classified with the gate's own regex before its Rust
result was read, and the R3 cases were checked against the per-case receipts `green-run.py`
asserts (device destroy, maps, case complete, probe-restart counts, the eight
transient-depth receipts of `depth-refusal-eight`, no `SKIP`) plus the in-process pixel
oracle. Receipts: `logs/` (per-run logs gzip'd under `logs/runs/<label>/`), tables
regenerated by `scripts/verify_tables.py` into `logs/verify-tables.md`.

On red3 each GPU test fails its Rust assertion with the captured report, e.g.
`assertion left == right failed: the batch fence was used by two threads at once —
["UNASSIGNED-Threading-MultipleThreads-Write: vkQueueSubmit(): THREADING ERROR : object of
type VkFence is simultaneously used in current thread … and thread …"]`, and the same
report is in stdout for the gate. The pure tests use the new types, so on the unfixed tree
they cannot compile; their RED is a compile failure, and the behavioural RED/GREEN is
carried by the two GPU tests.

History, kept because it is evidence too:

* **v1** (`fix-v1-engine-local.patch`, latch inside `queue_owner.rs`): before/after equal to
  the table above (held-open 0/50, narrow 0/30, other extra-default 0/20 each, same unit
  groups clean). Its red variant showed the limitation that led to v3: the layer flagged
  every invocation (10/10, 20 reports), but the GPU tests' Rust assertions passed on the
  unfixed engine (10/10), because on Lavapipe the fence signals ~35 ms after
  `vkQueueSubmit` returns.
* **v2** (`fix-v2-global-capture-rejected.patch`, latch in core, messenger in every test
  `DeviceContext`): rejected. VVL stops its default stdout logging while an application
  messenger is registered, so red2's reports appeared only inside the panic text and none
  reached stdout — the R9 gate would have been blind for the whole lib test binary. The v2
  chain was stopped and its API-clean readings are not counted; only its core-module and
  Rust-level ring results were valid. v3 scopes the messenger to the two tests and
  re-emits each report in the layer's format, which the red3 rows above confirm.

## Hot path

Uninstrumented counters printed by the held-open case (medians; "before" n = 50 on the
tested tree, "after" n = 50 on fixed3):

| counter | before | after |
|---|---|---|
| `batch_flush_submit_us` (handoff incl. the new latch allocation) | 10 µs | 12 µs |
| `batch_flush_finish_us` | 26 µs | 24 µs |
| `queue_async_queue_us` (handoff → owner pickup) | 40.5 µs | 46.5 µs |
| `queue_async_driver_us` (owner's `vkQueueSubmit`) | 2578 µs | 1686 µs |
| narrow policy, `batch_flush_submit_us` | 13 µs | 12.5 µs |

The handoff cost moves by about 2 µs (within run-to-run spread: the narrow pair moves the
other way). The owner's `vkQueueSubmit` is faster after the fix because the layer no longer
formats and logs a collision inside it. Whole-process time is dominated by device
creation, shader compilation and teardown and is not a hot-path measure: it moved
1123 → 1224 ms (default) and 1379 → 1355 ms (narrow), and the unfixed red3 binary measured
1540 ms in the same session, so it reflects host load at the time rather than the fix.

## Not verified

* The `vkResetFences`-during-the-tail-of-`vkQueueSubmit` overlap was never observed on
  Lavapipe (its fence signals after the call returns); the fix covers it by construction.
* Only Lavapipe under VVL 1.4.309; no native GPU, MoltenVK or other driver.
* The host-window present path was not exercised (no window in these tests); DIAGNOSIS.md
  argues it is unaffected.
* Of `green-extra-narrow`, only `held-open-off` was run (30 times before and after).
* A real owner stall at the 5 s deadline was not provoked on a device; the deadline and
  abandonment are covered by the core and queue-owner unit tests.
* Clippy was not run.

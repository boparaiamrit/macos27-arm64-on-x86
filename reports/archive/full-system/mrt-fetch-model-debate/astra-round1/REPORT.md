## A. Pool blocker: invalid portable assumption, high confidence

engine/desc_arena.rs:485-510 assumes twice maxSets guarantees exhaustion. vkAllocateDescriptorSets explicitly permits allocation failure on exceeding maxSets/type capacities; it does not require failure. Vulkan 1.0 without maintenance1 had remaining-capacity preconditions, but this Vulkan 1.2 environment is not that case. The component control supports the narrower conclusion that adding INPUT_ATTACHMENT reservation did not cause this failure. It is not a complete baseline renderer proof. Allocation success without a grow is correct when the driver returns success.

Smallest robust test seam: intercept the Vulkan device dispatch table/API functions used by the real DescriptorArena owner (create pool, allocate, free, destroy). Run its unchanged allocate/free control flow against a scripted fake device dispatch; record incoming VkDescriptorPoolCreateInfo and VkDescriptorSetAllocateInfo, return unique handles, and validate free ownership. This avoids a second allocator algorithm or a hard capacity policy. Alternatively extract only these four API operations behind a private adapter, with production delegation and scripted test implementation; do not duplicate the arena decision loop.

Script existing-pool OUT_OF_POOL_MEMORY and FRAGMENTED_POOL independently, then fresh-pool success; assert exactly one creation, returned grew=true, appended block and proper free routing. Also exercise reverse-order fallback to an older successful pool with no growth. Script a fresh pool refusal: it must be destroyed once, not appended, return DescArenaAllocSetsGrown, and leave existing blocks intact. Exercise host/device OOM on existing allocation (no grow), pool creation (no append), and fresh allocation (destroy fresh pool, no append). Record free calls for sets from both pools and test failure attribution. The create call receipt must retain the real derived INPUT_ATTACHMENT budget and FREE_DESCRIPTOR_SET flag. Never call a real allocation and overwrite its successful result with an injected error: that leaks a set and invalidates the test's state. Replace the unportable scenario with deterministic error injection retaining its assertions; do not skip or loosen assertions. Keep successful real-device allocation/free as a separate smoke check.

Sources: [allocation result contract](https://docs.vulkan.org/refpages/latest/refpages/source/vkAllocateDescriptorSets.html); [07895/07896 version conditions](https://docs.vulkan.org/refpages/latest/refpages/source/VkDescriptorSetAllocateInfo.html).

## B. Confirmed P1: sparse table admission omits the stage span limit

engine/color_input.rs:65-69 checks count only. engine/caches.rs:646-659 emits span entries, including UNUSED holes, and :2287 supplies that length as inputAttachmentCount. With maxColorAttachments=8, stage input limit=4, set input limit=4, selection {7} passes the count check yet creates an eight-entry subpass table. Confidence: high; this is conditional on a narrower host, not demonstrated on this llvmpipe run.

VUID-VkSubpassDescription-inputAttachmentCount-12293 limits inputAttachmentCount itself to maxPerStageDescriptorInputAttachments. The live refpage returned by one fetch omitted this newer text; the full current normative render-pass chapter includes it. [Normative chapter](https://docs.vulkan.org/spec/latest/chapters/renderpass.html#VUID-VkSubpassDescription-inputAttachmentCount-12293).

Actual descriptor semantics matter: engine/exec.rs:2984-2990 builds one FRAGMENT INPUT_ATTACHMENT binding of count=1 at 192+N for each selected slot. engine/caches.rs:2046-2053 translates that exact list to the descriptor layout. This is a per-draw sparse layout, not an eight-element descriptor array: {7} uses one descriptor at binding199. UNUSED subpass holes do not reserve descriptors. [Pipeline-layout rules 03021 and input-attachment aggregate rules](https://docs.vulkan.org/refpages/latest/refpages/source/VkPipelineLayoutCreateInfo.html).

Minimal owner fix: retain raw maxPerStageDescriptorInputAttachments separately in DeviceFeatures, alongside the existing min(stage,set) descriptor limit; admit span <= raw stage limit AND count <= existing merged limit. Preserve ordinal holes. Do not simply change count to span against min(stage,set): stage8/set4 with {7} is legal and would be falsely refused. RED engine/color_input.rs:169 cannot distinguish these capabilities and would permit that overrestrictive fix. Add stage4/set8 rejection and stage8/set4 acceptance, plus descriptor-count excess, using explicit physical-capability values. Update the old fixture asserting {7} with descriptor limit1 to express its intended stage limit independently.

## C. Confirmed P1: primary entry/readback layouts disagree under COLOR_GENERAL=off

Scenario: selected input0, non-feedback/non-imported target. engine/caches.rs:665-666 chooses GENERAL during the pass; :676-682 exits COLOR_ATTACHMENT_OPTIMAL. A seeded Preserve draw transitions to GENERAL at engine/exec.rs:4542-4546 (also seed-copy/resident-source branches), but render-pass creation at engine/caches.rs:2152 declares the LOAD initial layout as COLOR_ATTACHMENT_OPTIMAL. That violates initialLayout matching at pass begin. After pass end, engine/exec.rs:5561 names GENERAL as the transfer barrier's oldLayout, despite the actual final layout being COLOR_ATTACHMENT_OPTIMAL; :5592 restores GENERAL while :5690 registers COLOR_ATTACHMENT_OPTIMAL. Confidence: high, static contract violation; pixels cannot validate it. Input0 existed in baseline, so distinguish this inherited narrow-policy defect from a newly introduced secondary-input defect.

Minimal consistent change using the existing explicit-transition architecture: primary Preserve initial layout = key.color_layout(0); elide the ready ColorWrite barrier only when tracked layout equals that entry layout; readback starts from and restores key.color_final_layout(0); registry continues recording that same final layout. Keep Clear/Undefined behavior, imported GENERAL, and feedback layout selection intact. Probe restart must transition actual final to declared entry for every loaded attachment, not only primary. This avoids changing the resting-layout policy or pretending post-readback state is the subpass layout.

Counterargument to hypothesis C: current ready-primary elision at engine/exec.rs:6466-6467 is NOT by itself invalid. A resident left at COLOR_ATTACHMENT_OPTIMAL already matches the CURRENT LOAD initial layout; Vulkan can transition it to GENERAL at subpass entry. Thus RED engine/exec.rs:8711 is a necessary regression for the proposed explicit-entry contract, not independent proof the old ready path is wrong. Changing that predicate alone would create a mismatch with the old LOAD initial layout. Conversely, preserving initial=final and changing every pre-pass transition target is another valid architecture, but is a broader change than aligning primary with the existing secondary explicit-entry owner.

Sources: [vkCmdBeginRenderPass initialLayout-00900](https://docs.vulkan.org/refpages/latest/refpages/source/vkCmdBeginRenderPass.html); [VkImageMemoryBarrier oldLayout-01197](https://docs.vulkan.org/refpages/latest/refpages/source/VkImageMemoryBarrier.html).

## D. Additional P2: primary-only restart fix misses MRT attachments

engine/exec.rs:5434 gates PASS_CHURN on primary load and primary non-feedback, then :5476-5478 replays the entire original rp_begin. With COLOR_GENERAL=off, selected secondary1 and sec.load=true, the first pass leaves secondary1 COLOR_ATTACHMENT_OPTIMAL while engine/caches.rs:2185-2188 requires GENERAL at the second begin. The existing barrier at :5458-5466 touches only target_image. RED engine/exec.rs:6470 and :8717 preserve that single-primary scope, so their fix/test cannot catch this secondary mismatch. Confidence: high; probe-only trigger, not evidence the default GPU cases failed. This secondary initial/final divergence is introduced by indexed-input handling. Same normative 00900 applies.

Related inherited probe defect: a preserving primary can coexist with CLEAR secondaries or depth/stencil. Replaying the original pass clears them again despite no draws; primary load alone does not establish pixel neutrality (engine/exec.rs:5434, :5476; engine/caches.rs:2185-2191). Do not claim this was introduced by the MRT delta. Correct restart ownership should derive a preserving compatible pass for all attachments and transition each from its actual final layout to that pass's initial layout. If deliberately narrowing probe applicability instead, report unsupported shapes explicitly; do not silently characterize a narrower probe as universal. Add a secondary-only selected LOAD restart test and a mixed primary LOAD/secondary CLEAR preservation test.

## Assessment of the five proposed tests

The before/red diffs are mechanically behavior-preserving: LOAD logic is extracted unchanged; readback/restart barriers reproduce existing fields; the additional next-layout argument is initially ignored. No semantic fix is embedded. Four primary tests explicitly require COLOR_GENERAL=off, so run them in a separate fresh process with that configured before cached config initialization. Under default settings their precondition assertion fails; that is not a behavioral RED. A general suite plan must account for this requirement explicitly.

The readback test covers both directions, but should also connect restored layout to registry publication and cover imported/feedback policies. The primary LOAD test connects the real pass constructor helper. The ready-path test encodes the selected new architecture as explained above. Restart test is too narrow for MRT. Span test requires separate stage/set fields and the legal sparse counterexample. These are owner tests, not substitute validation-layer or guest proof.

The standalone transfer-copy oracle passed on the actual pinned Lavapipe runtime. The exact embedded scatter shader also compiled and executed successfully, both with minimal Vulkan device features and with robustBufferAccess enabled. The QEMU LLVM abort was therefore not reproduced by this isolated shader/process.

Each execution checked all 2,048 destination words. Three runs copied 257, 7 and 513 words from source offsets 17, 401 and 1,000 to separated destination offsets 31, 700 and 901. All 777 copied words matched the known source ramp; all 1,271 gap words retained their sentinel. Fence completion and host-read visibility were required before validation.

Actual runs, each in a fresh process/container/tmp:

- transfer: PASS, Vulkan vkCmdCopyBuffer with three regions, no compute pipeline.
- compute: PASS, exact 411-word SPIR-V creation, pipeline creation and dispatch.
- compute-robust: PASS with advertised robustBufferAccess enabled, matching this production core feature.
- transfer-robust: PASS with the same robust feature enabled.

The source-supported LP_NATIVE_VECTOR_WIDTH=128 experiment was not run because default compute did not reproduce the abort. No production capability, driver, LLVM flag, pipeline, guest image, source file or launcher was changed. The existing transfer-copy fallback remains a justified mitigation candidate, but its production flags have not been live-qualified by this probe.

Driver properties: llvmpipe (LLVM 20.1.2, 256 bits), Mesa 25.2.8-0ubuntu0.24.04.4. The exact shader is the 411-word GUEST_SCATTER_SPIRV from engine/scatter_shader.rs, SHA-256 of little-endian SPIR-V bytes ce957c1f75216dccb5558886dcf0d15ecd57c2c3b4642f12195af10c171eebe9. The retained header is extracted with exact declaration/count/header checks, not regenerated by a shader compiler. See shader-provenance.json.

The C probe uses the builder's installed official Vulkan headers and loader. It creates three ordinary coherent host-visible storage/transfer buffers, a single compute-capable queue, bounded barriers and a 30-second fence wait. For compute it creates the exact three-storage-buffer descriptor layout, four-byte run-count push constant and main entry point. This matches ScatterPipeline's relevant shader/layout construction, but not the entire production DeviceContext extension/feature chain or prior pipeline/process state. No guest RAM import is needed. Minimal-device and robust-feature source/binary versions are retained separately.

Core containment: supervisor writes/readbacks /proc/self/coredump_filter=0x10 and verifies it survives fork/exec in a noncrashing child. The actual native probe repeats the write/readback after exec before loading Vulkan. No global core_pattern/WSL setting was changed. No owned crash core was created. This verifies configuration/inheritance, not an empirical core-size limit under a crash.

Commands were guarded every 0.2 seconds against a stale/future host-space sample and the unconditional 10 GiB floor. Limits: two CPUs, 2 GiB memory/equal swap, PID 128, no network, read-only root, 64 MiB tmpfs, 300-second overall command deadline and owned-process-group cleanup. All owned containers are gone. No VM ran or QEMU build occurred. Exact minimum free-space observations, artifact/library hashes, subsecond/second-scale timings and complete logs are in handoff.json and per-stage result files. Total retained logs are below 2 KiB.

Interpretation: the transfer route has a real byte-correct software-Vulkan execution witness. The exact scatter shader is not unconditionally rejected by this Mesa/LLVM version. Additional QEMU/Reims device features, pipeline history or process state remain possible differentiators; none is established as the trigger. There is no desktop, hardware acceleration or complete production-workaround claim.
